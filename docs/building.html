Extending and shipping

Building and publishing

Build Project turns your project into a standalone game for the computer you're on. publish.py packages Empire Engine itself (Hub, editor and player) for release.

Building a game

  1. Save. The build uses the files on disk; unsaved edits are not included.
  2. Choose File > Build Project…, pick a folder outside the project, enter a name for the game, and choose its Platform (Windows, Mac or Linux) and Architecture (the kind of processor). Both start on the computer you're on.
  3. Wait while it builds (it can take a minute). When it's done, Open Folder shows the game. If it fails, Copy Errors copies the full error report, and the whole log is in empire-build.log in your temp folder.

The scene open in the editor is the scene the game starts with.

What a build contains

<name>  (or <name>.exe)     the game: run this
...                          the .NET runtime and native libraries (Vulkan, GLFW, audio)
libvulkan.1.dylib, vulkan/   macOS only: the bundled Vulkan loader and MoltenVK
GameData/
  game.json                  the game's name and start scene
  Scripts.dll                your scripts, compiled
  EmpirePackage.*.dll        the project's installed packages
  Core/                      a copy of the project: Scenes/, Models/, Audio/ ...
  • Self-contained: the .NET runtime is included, so players need nothing installed. On Macs, Vulkan is bundled too (Intel Mac builds are experimental: they carry their own native libraries, see Tools/IntelNatives, and have only been tried under Rosetta); on Windows and Linux players need a graphics driver with Vulkan, which current drivers include.
  • For one platform: each build is for the platform you chose. See Building for another platform.
  • Scripts are compiled at build time. The game only loads Scripts.dll and never compiles anything. The Scripts/ and Packages/ folders are not copied into Core/.

What you need to build

Build Project takes the player from one of two places, and uses the first it finds:

  • A released editor (installed from the Hub) carries the player already built: its own files are in the Player/ folder next to empire.dll (on a Mac, inside the editor app), and the files it shares with the editor are kept once, beside the editor. Building copies them, names the program after your game, and adds your project's content and compiled scripts. Nothing needs to be installed, not even the .NET SDK.
  • An editor run from a checkout of this repository (with dotnet run --project Editor, or the Hub built from source) has Player/Player.csproj in a folder above it. Building then runs dotnet restore and dotnet publish on it, which needs the .NET 10 SDK.

What a game leaves out

To keep games small, a game doesn't carry all of .NET. It leaves out libraries nothing in the engine uses, such as networking (System.Net.*, including HttpClient), System.Data, XML (System.Xml), dynamic and expression trees, along with .NET's debugger files. It also has no shader compiler: Build Project compiles the engine's shaders into GameData/shaders.bin. The list is Player/LeftOutOfGames.targets.

The editor keeps everything, so a script that uses one of these runs when you press Play, but Build Project stops with a compile error. A package that uses one stops the build too. One case only shows up when the game runs: BRUTAL's own number types (Brutal.Numerics, such as float3) can't be written as JSON in a game, for example with SaveGame. Use System.Numerics types like Vector3 for anything you save. If you run the editor from source you can delete the library's line from the list, and the game will carry it.

If neither is found, the build stops with Could not find Player/Player.csproj in a folder above the Editor, or a built Player folder next to it.

Building for another platform

You can build for Windows, Mac or Linux from any of them. A game for another platform or processor goes in a folder of its own, <name>-<Platform> such as MyGame-Windows, or <name>-<arch> such as MyGame-x64 for another processor on your own platform, so different builds never mix.

  • Architecture: the dropdown lists the processors .NET runs on for the chosen platform. Windows: x64, arm64 and x86. Mac: arm64 (Apple Silicon) and x64 (Intel). Linux: x64, arm64 and arm32. There is no 32-bit Mac build and no 32-bit ARM build for Windows, because .NET doesn't support them.
  • Which ones start: BRUTAL, the library the engine draws with, only ships its native libraries for x64 Windows and Linux and for Apple Silicon. Empire Engine carries its own for Intel Macs and Linux arm64 (see Tools/IntelNatives), so those games are experimental: they build and have started under emulation (Intel Mac under Rosetta, Linux arm64 on a simulated Raspberry Pi-style Debian system), but haven't been tried on real hardware. Windows arm64, x86 and Linux arm32 games are built but won't start yet. The editor warns you when you pick one of these.
  • Without a release: the releases carry players for x64 and arm64 on all three platforms, plus Intel Mac. A released editor can't build x86 or arm32, since there is no player to take, and says so. An editor run from a checkout can.
  • A released editor needs the player for that platform, so the first build for it downloads the matching editor zip (around 50 MB) from the same version's GitHub release. The player is kept in <application data>/EmpireEditor/Players/, so later builds need no internet connection.
  • An editor run from a checkout of this repository runs dotnet publish for that platform instead, which downloads what it needs the first time. It can only build a Mac game on a Mac, because the game has to be signed there.
  • Built on Windows for Mac or Linux: Windows can't mark the file as a program, so run chmod +x "<name>" in the game's folder on that computer first. The editor reminds you when the build finishes.
  • Try the game on the real platform before you ship it. Building it doesn't run it.

Running the game

  • The game opens in a window and plays its start scene through the scene's first camera (if a scene has no camera, the view orbits the scene).
  • F11 switches between a window and fullscreen. Fullscreen uses the monitor's largest 16:9 mode; other shapes are letterboxed.
  • Save games go in <application data>/<game name>/Saves/.
  • If a script fails to load, the game prints the errors and exits.
  • The game uses Empire Engine's crown icon: on its .exe and taskbar button on Windows, its window on Linux, and in the Dock on macOS.
  • Every game opens with a splash screen showing the Empire Engine and BRUTAL logos and BRUTAL's copyright notice, for about 3.5 seconds, before any scene loads or script runs. It can't be turned off or skipped: the BRUTAL License requires the BRUTAL logo in every product built with it. See below.
  • The game's UI is drawn over the game view and works exactly as in the editor's play mode. Its font is built into the engine, so there's nothing extra to ship.

The splash screen

Games open on a dark screen with Empire Engine's crown and name, then "built with" and the BRUTAL logo, and under it BRUTAL's copyright line and web address. It fades in over half a second, holds for two and a half, and fades out. Nothing else happens until it ends: the scene isn't loaded and no script's Start runs. Time spent minimized doesn't count.

It's there because Empire Engine is built on BRUTAL, whose license (section 2.2) says the BRUTAL logo must be shown before gameplay in every product built with it, unaltered except for scaling, for long enough to read, and no less prominently than other logos. So the BRUTAL logo is the official one, drawn larger than Empire Engine's, and the screen has no skip. The notice file (NOTICE.txt) and the credits for every other library go into Licenses/ next to the game.

  • The code is Engine.Brutal/Ui/SplashScreen.cs, and the logos are embedded in Engine.Brutal.dll, so there's nothing to ship separately.
  • Don't edit, recolor or crop the logo, and read Engine.Brutal/Ui/Logos/README.txt before changing the screen. If you ever want it gone, you need written permission from Ahwoo Limited (the BRUTAL license allows asking).
  • The editor and the Hub open on the same screen (the Hub's is an overlay in Hub/MainWindow.axaml, using the same logo files), and they carry the full credits under Help > Credits and About.

Packaging Empire Engine for release

publish.py publishes the Hub, the editor and the player as two separate packages for each platform, ready to zip and ship. The Hub package doesn't include an editor: people install one from inside the Hub (see Install version…), which downloads the editor package from your GitHub release. It needs the .NET SDK and Python 3.

# for the platform you are on
python3 publish.py

# for several platforms, zipped
python3 publish.py --rid win-x64 --rid linux-x64 --zip
OptionMeaning
--rid PLATFORMA platform to build for: osx-arm64, osx-x64, win-x64, win-arm64, linux-x64 or linux-arm64. Repeat for several. Defaults to this computer's.
--out FOLDERWhere packages go (default Empire/ next to the script, which git ignores)
--zipAlso zip each package: EmpireEngineHub-<version>-<platform>.zip (the Hub) and EmpireEngine-<version>-<platform>.zip (the editor)
 
EmpireHub.exe            the Hub: run this
Empire Engine Hub.app    the Hub, as a Mac app: drag it into Applications
Empire/<version>/        what the Hub unpacks into <hub>/Empire/<version>/
  empire                 the editor (empire.exe on Windows)
  Player/                the game player's own files; what it shares with the editor sits beside the editor
Empire/<version>/
  Empire Engine Editor.app    the editor and the game player, as a Mac app

To try the Hub with an editor before a release exists, copy the Empire/ folder from the editor package next to EmpireHub (on a Mac, into ~/Library/Application Support/EmpireHub/, where the app keeps its editors).

The Mac apps

On macOS the Hub is packaged as Empire Engine Hub.app and the editor as Empire Engine Editor.app (inside the editor package's version folder; the game player is inside it too, so Build Project still finds it). Both are built the same way. The Hub: Contents/MacOS holds the Hub and everything it needs, Contents/Resources the icon (EmpireEngineIcon.icns, made by Tools/make_icons.py), and Contents/Info.plist says what the app is. publish.py builds it and signs it ad hoc (no Apple developer account), then zips it with macOS's own ditto, which keeps the signature (an ordinary zip drops it and macOS would call the app "damaged"). So make the release zips on a Mac; publish.py warns if it can't. The app is not notarized, so the first time someone opens it macOS asks them to confirm (right-click the app, choose Open). Because the app is left exactly as shipped, it keeps the editors it installs in ~/Library/Application Support/EmpireHub/Empire/. The Hub starts an editor by running the program inside its app, in the project's folder.

One detail of the editor app: macOS code signing refuses to sign an app that holds a folder named like icd.d (a dot and a short extension), so inside the editor app the Vulkan driver folders (vulkan/icd.d) are named icd. The editor and the games it builds find either name, and a built game keeps the name it was given. An older Hub (0.2.2 or earlier) can't install the Mac editor app: it only knows the plain folder, and says so. Update the Hub first.

Mac packages (osx-arm64 and osx-x64) carry their own Vulkan loader and MoltenVK from ThirdParty/Vulkan/osx-arm64 or osx-x64. If that folder is missing, the script says so; restore it, or set the EmpireVulkanLoader and EmpireMoltenVK environment variables to the paths of libvulkan.1.dylib and libMoltenVK.dylib.

Publishing a release

The Hub's Install version… button reads the project's GitHub releases. To make a version installable:

  1. Bump the version (EmpireVersion in Directory.Build.props) and commit it.
  2. Build the zips on each platform you support: python3 publish.py --zip makes two in Empire/. EmpireEngine-<version>-<platform>.zip (for example EmpireEngine-0.1.1-osx-arm64.zip) is the editor, which the Hub's Install version… downloads; it holds Empire/<version>/empire.dll, and that name and layout are required. EmpireEngineHub-<version>-<platform>.zip is the Hub itself, for people to download first.
  3. Create a release on GitHub (Releases > Draft a new release) with a tag that is the version, v0.1.1 or 0.1.1, and attach both zips as release assets. GitHub adds a checksum to each asset, and the Hub checks it.
  4. Publish it. Drafts aren't shown. Tick Set as a pre-release for a beta, and it appears in the list marked Pre-release.
  • Installed Hubs update themselves from the EmpireEngineHub-<version>-<platform>.zip in a release (see Updating the Hub), so attach it for every platform. A release without a Hub zip for someone's computer simply offers them no update.
  • Don't rely on GitHub's automatic "Source code" zips: they hold source, not a built editor, and the Hub never offers them.
  • A release only needs the platforms you've built. Someone on another platform sees No download for <platform>.
  • The repository the Hub reads is set in Hub/Releases/ReleaseCatalog.cs (Repository). A fork should change it. Setting the environment variable EMPIRE_RELEASES_URL to a releases-list address makes the Hub read that instead, which is how the tests and demos fake GitHub.

Versioning

The Empire Engine version (currently 0.3.3) is set once, as EmpireVersion in Directory.Build.props, and shared by the editor, the player and the Hub. Bump it there for a release. New projects record the version they were made with, and the Hub opens each project with that version when it's installed.
