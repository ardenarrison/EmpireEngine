Engine architecture

How the projects in the repository depend on each other, what runs in one frame, and how the editor and a built game share the same code. For people working on Empire Engine itself.

All projects target net10.0. The version lives in Directory.Build.props; Directory.Build.targets handles platform details such as bundling Vulkan on macOS.

One frame

SceneUpdate.Update(scene, dt) in Engine.Core is the whole simulation for one frame. The editor's play mode and the built game both call it, which is why they behave the same:

Time.Advance(dt);
Input.Advance();
SceneManager.Process(scene);   // scenes and saved games asked for last frame arrive before scripts run
GameUi.Update(scene);          // clicks and typing on the game's UI, and their OnClick-style handlers
ScriptRuntime.Run(scene);      // Start (once), then Update, for every script
// Spin components turn
scene.Physics.Update(scene, dt);
Animators.Update(scene, Time.deltaTime);
Particles.Update(scene, Time.deltaTime);
Audio.AudioEngine.Update(scene, dt);

The host then draws: SceneLighting.Collect gathers the sun, the Environment and up to 16 other lights; the host calls IRenderer.SetShadows, SetLighting, BeginFrame, DrawModel for every Mesh (with its animation pose), DrawParticles, and EndFrame. BrutalRenderer queues the draws so it can render the sun's shadow map from them first, then draws the sky, the solid models and then the see-through ones. Particles are drawn after the models with blending, and IVulkanRender scripts record their commands inside the same scene pass.

Scripts from source to running

  1. Visual scripts: VisualScriptSync turns each .visualcode into a .cs next to it.
  2. Packages: Packages.Build compiles each turned-on package whose stamp is out of date into Packages/EmpirePackage.<Id>.dll.
  3. Scripts: ScriptBuilder.Compile compiles every .cs in Scripts/, plus a file of global usings, into one DLL (optimized, unsafe allowed), referencing the engine and the package DLLs.
  4. Loading: ScriptRuntime.Load looks up each Script component's class by name (the project's DLL first, then the packages), creates an instance, and copies the Inspector values in with ScriptFields.Apply. A Behaviour stays on its Script component; a custom component is inserted on the object right after it.
  5. Running: ScriptRuntime.Run calls Start once and Update every frame, catching exceptions per script.

In the editor the DLL goes in a temp folder with a fresh name each play, and package DLLs are read into memory first so they can be rebuilt while the editor runs. Built games compile once, at build time.

Play mode in the editor

Pressing Play saves a snapshot of the scene to a temp file, compiles and loads scripts, resets time, input, animators and particles, and switches to drawing through the scene camera. Stop reloads the snapshot, so nothing that happened while playing sticks. Undo works the same way: each settled edit stores the scene's JSON.

Assets

AssetCache loads each model, image and sound once by its path in the project. ModelLoader picks GlbLoader, FbxLoader or ObjLoader by extension; all produce the same GlbModel (meshes, materials, nodes, skins, clips). The editor checks file times once a second and re-uploads models that changed. When a scene loads in the background, SceneManager.AssetWarmer loads its assets on that thread.

Physics

PhysicsWorld steps at 60 Hz, up to 5 steps a frame. Each step rebuilds bodies from the scene, integrates forces, finds contacts (sphere, box with a 15-axis separating axis test, convex hulls, and triangle meshes through a tree), solves them with warm-started sequential impulses, moves the objects, then raises collision events by comparing this step's touching pairs with the last.
